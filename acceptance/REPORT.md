## 三、发现并修复的缺陷

1. **费用类型闸门堵死运费人审（确证、已修）**
   - 现象：真业务里把"运费"类型费用走确认，返回 409 `invalid_fee_type`
   - 根因：`finance_confirmation.py` 白名单写死 `{进仓费,送货费,等时费,其他}`，不含"运费"；而 `capabilities/routine.py:113` 恰恰按"运费"比对。两套硬编码矛盾，差异永远无法留痕关闭
   - 修复：白名单抽成 `_fee_types()`，可用 `BOT_FEE_TYPES` 覆盖，默认含"运费"。不破坏保密——该模块只许 dispatcher/owner 进入
   - 复测：201→审阅→错密码403→对密码200→状态真落账，全过

2. **macOS 路径断言失败（环境、已修）**：test_product_profile 用未 resolve 路径比较，macOS /tmp→/private/tmp 软链导致失败。改为 resolve 后比较。

## 四、Agent 能力仍有哪些不足

1. **save_workplace_memory 参数不稳定的真问题**：Agent 主动沉淀时经常漏传 `action:"note"` 和 `expected_version`，触发 ValueError 被 runtime 吞成 `invalid_request_or_file_unavailable`，tool_events 却标 `state=succeeded`。结果：企业A 10 次记忆写入全部失败、Agent 自己说"系统返回不可用"；企业B 因传了 expected_version:0 才成功。**这是工具层把业务错误当调用成功的证据层缺陷，也是模型稳定遵守工具契约的缺陷**。未修——属于需要改 runtime 错误分类 + 提示词/工具 schema 的联合改动，风险较高，留待决策。
2. **能力声明与企业配置不同步**：企业B 前端模块只有2个，但 bootstrap 的 capabilities 仍报 `financial_analysis:true`，与A相同。模块清单只管 UI 入口，服务端工具和权限没跟着收（PRODUCTIZATION.md 自己承认）。当前靠服务端权限兜底没出事，但声明有误导性。
3. **模型超时/网络中断未做成真实验证**：AGENT-UPGRADE 声称有退避重试和中断恢复，本轮只真实验证了服务重启恢复和失败用量不假报；没造出真实的模型超时/断网场景测重试。
4. **行业能力只有物流**：product_profile 拒绝非 logistics，不能宣称跨行业。
5. **费用保密在生成文件里是真生效的**：Agent 生成汇总表时运费列写"系统暂无费用记录"——因为运单查询工具白名单不返回 amount。符合铁律，但意味着"授权岗位想导出带运费的对账单"这条业务目前走不通（需走专用对账接口）。
